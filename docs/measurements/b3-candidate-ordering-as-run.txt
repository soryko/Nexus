AS RUN — B3 candidate ordering, tools/measure_candidate_selection.py.

Produced during the B3 review, after the three harness corrections that review found:

  1. The result-identity assertion compared only the walk from page one, so the separately
     measured deep page was checked by row count alone. A mutation that shifted the
     10,000-depth page by 20 memories passed every check in this harness. Both measured
     depths are now compared by value -- hits, order, complete evidence, pagination.
  2. The identical-run latency spread took the maximum directional ratio across shapes and
     reciprocated only that winner, understating the spread. Each pair is now made
     symmetric before the maximum.
  3. That spread was printed as a bare aggregate, so no run of this harness could be
     rechecked once correction 2 changed the formula that produced it. Not this milestone's
     own as-run file -- benchmarks/dev/results-candidate-ordering.txt exists and carries the
     original 1.03x, but not the paired latencies behind it -- and not the three runs made
     under the corrected formula either. The paired per-shape values the ratio is taken over
     are now printed with it, per shape and once as a line of JSON. This is the first run of
     this harness whose spread can be recomputed from the file it is archived in:
     max over shapes of max(a/b, b/a) over the pairs in the "spread inputs" line, which is
     commit_exact's 8.379 / 8.054 = 1.04. That line was printed rounded to three decimals,
     so this file recomputes its spread only to that rounding; the tool now prints the
     paired values unrounded, and runs archived after it recompute exactly. The first
     such run is archived beside this one, in
     docs/measurements/b3-candidate-ordering-precision-as-run.txt; its callback figures
     reproduce this file's exactly, and only its latencies differ.

No correction moves a measurement. Every callback figure below matches the run that produced
the tables in docs/plans/milestone-b3-candidate-ordering.md exactly, and those figures are
deterministic -- the repeatability control asserts them equal across two fresh copies rather
than observing that they were.

The latency spread is per-run, and it describes this instrument's noise rather than bounding
anything. Four runs on this machine have given 1.06x, 1.42x, 1.05x and 1.04x (this file); the
plan cites 1.42x as the widest. Only this run's inputs survive, so the other three stand as
reported and cannot be rechecked. Environment: CPython 3.13.15, SQLite 3.53.4 (.venv-sqlite).

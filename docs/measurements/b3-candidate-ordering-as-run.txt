AS RUN — B3 candidate ordering, tools/measure_candidate_selection.py.

Produced during the B3 review, after the two harness corrections that review found:

  1. The result-identity assertion compared only the walk from page one, so the separately
     measured deep page was checked by row count alone. A mutation that shifted the
     10,000-depth page by 20 memories passed every check in this harness. Both measured
     depths are now compared by value -- hits, order, complete evidence, pagination.
  2. The identical-run latency spread took the maximum directional ratio across shapes and
     reciprocated only that winner, understating the spread. Each pair is now made
     symmetric before the maximum.

Neither correction changes a measurement: every callback figure below matches the run that
produced the tables in docs/plans/milestone-b3-candidate-ordering.md exactly. What changed
is what the harness retains and asserts, and the latency-spread line.

The latency spread is per-run. Three runs on this machine gave 1.06x (this file), 1.42x and
1.05x; the plan cites 1.42x as the widest. Callback counts are deterministic and repeated
exactly. Environment: CPython 3.13.15, SQLite 3.53.4 (.venv-sqlite).

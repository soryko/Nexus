# Nexus Memory — milestone B: repository-aware search

Proposed scope: add exact and lexical retrieval over stored memories, scoped tag and kind filters, a launch-bound repository identity that the server verifies rather than trusts, and caller-supplied file and symbol references. Do not add embeddings, ranking models, relevance learning, or any claim of retrieval quality; those belong to milestone C and to the evaluation milestone. Milestone A's durability, idempotency and conflict guarantees must survive unchanged.

Status: draft for approval. No code until the shared contracts below are accepted.

## Shared contracts and decisions

- Layout stays `src/nexus_memory/{domain,storage,memory,transport}/`. Search is a repository capability behind the existing protocol and a service method, not a new subsystem or a second store. The MCP layer keeps adapting schemas and errors only.
- Retrieval is lexical and exact. `search` ranks with SQLite FTS5 BM25 over current revision bodies, with a deterministic tiebreak on `durable_seq` descending then `memory_id`, so identical corpora return identical orderings. No stemming beyond FTS5's `unicode61` tokenizer, no synonyms, no query rewriting, no model call anywhere on the read path.
- The lexical index is derived state maintained inside the same write transaction as the revision it describes. FTS5 is local and cheap, so this preserves atomicity and gives read-your-writes without a worker. The outbox stays, and its meaning narrows: it now exists for the future embedding index, which does need model calls off the write path. `status` must distinguish `lexical_index: available` from `derived_indexes` that remain unavailable.
- Refuse to start when the runtime's SQLite lacks FTS5, reporting `unsupported_runtime` with the same startup discipline as the version floor. Detect by compile option, not by exception.
- Migration `002` is additive and transactional: it creates the index tables and backfills every current revision in the same transaction. Unknown future schema versions are still refused. A failed migration leaves the database at version 1.
- `search(query=None, tags=(), kinds=(), path=None, commit=None, limit=20, cursor=None) -> SearchPage`. Every filter is conjunctive. An empty `query` with filters present is a valid filter-only listing ordered by recency. `limit` is 1..100. Pagination is a keyset cursor over the ranking key, opaque to callers, and never a SQL offset.
- `SearchHit` carries `memory_id`, `revision_id`, `kind`, `tags`, `created_at`, `score`, and a `snippet`. The snippet is a bounded excerpt of stored bytes, never a summary or a paraphrase, and it inherits the rule that stored content is data and never instructions to the consuming agent. Hits carry references, not full bodies; callers reach the body with `get`.
- Forgotten memories are absent from every search path. The tombstone transaction deletes the memory's index rows, and search asserts against tombstones independently rather than trusting index deletion alone. A search must never be the way a forgotten body comes back.
- Search is scoped by both namespace and actor, exactly as reads are today. Add a scope-isolation test at the search boundary; a ranking index is a new way to leak across scopes.
- Repository identity is bound at launch by an optional `--repo <absolute path>`, never supplied by an MCP tool, matching the namespace and actor trust model. The server resolves the path once, refuses a path that is not a repository, and records the resolved root.
- Commit verification uses the `git` binary when it is present, checking `rev-parse --verify <oid>^{commit}` against the bound repository only. When `--repo` is absent or `git` is unavailable, verification is unavailable, not assumed: every stored identity records `verified` or `unverified`, `status` reports which mode the server is in, and no result is ever labeled verified without an actual check. Never fetch, never touch a remote, never run a git command with caller-controlled arguments beyond a validated object id.
- Milestone A's `snapshot` field stays exactly as it is — caller-asserted, unverified, unfetched — and is not silently upgraded. Verified identity is a distinct field with a distinct name so that existing memories are not retroactively given a guarantee they were never checked against.
- File references are `(path, symbol=None, line_start=None, line_end=None)`. Paths normalize to repository-relative POSIX form and are rejected if they escape the root, are absolute, or contain traversal segments. At most 16 references per revision. A path is verified when it existed at the verified commit, checked by `git cat-file -e <oid>:<path>`.
- Symbols and line ranges are **not** verified in this milestone. They are caller-asserted strings and integers, stored, filterable by exact match, and labeled unverified in every output. Verifying a symbol needs per-language parsing, and asserting a guarantee we do not compute is exactly the overclaim this project avoids.
- References are part of a revision, so `revise` replaces them wholly and omitting them clears them, consistent with the existing full-replacement rule. Reference changes flow through the same idempotency digest.
- The idempotency digest must include every new normalized field. A milestone-A key replayed with a milestone-B payload is an `idempotency_conflict`, not a silent acceptance.
- New expected errors extend `NexusError` with stable codes; add `invalid_query` for malformed FTS syntax so a caller can distinguish a bad query from an empty result. Public errors still carry no SQL, paths, content, scope details or stack traces.

## Task 1 — lexical index and search core

Add the FTS5 detection, migration `002` with in-transaction backfill, index maintenance inside the existing write boundary, and the scoped `search` service method with filters, ranking and keyset pagination. Write failing tests first and preserve the red/green evidence. Cover: index and body stay consistent across record, revise and forget; a forgotten memory is unreachable by every filter combination; scope isolation at the search boundary; ranking determinism across repeated runs and across a rebuilt index; keyset pagination returns each hit exactly once under concurrent writes; malformed queries raise `invalid_query` rather than leaking FTS errors; migration rollback leaves version 1. Extend the generated lifecycle model with search assertions rather than adding a parallel test corpus. Transport is task 2.

## Task 2 — repository identity, references, and transport

Add `--repo`, commit and path verification with an explicit unavailable mode, reference validation and normalization, the `search` MCP tool and the extended `record`/`revise`/`get` schemas. Add subprocess stdio tests covering the new tool schemas, filter-only search, paginated search, verified and unverified launches of the same database, principal and repository injection rejection, and traversal-escaping paths. Prove that a database written by a verifying server reads correctly on a non-verifying one and that nothing is relabeled. Update the README tool contract and the guarantees document with what verification does and does not establish. Run the full suite, build a wheel, exercise the installed entrypoint.

## Task 3 — independent review, benchmark and delivery

Review the complete diff against these contracts, focusing on index/tombstone consistency, scope isolation, transaction boundaries, migration behavior, git invocation surface, and the verified/unverified labeling. Benchmark index size and search latency at the existing 1,000 and 10,000 document points and record the deltas against milestone A's stored figures, labeling each number measured rather than estimated. Rerun the full suite, record actual output and runtime versions, and update `BUILD.json`.

## Evidence standard

Prove that search cannot return a forgotten body, cannot cross a scope, and cannot outlive a rolled-back transaction, and exercise those invariants with model and concurrency tests. Ranking determinism is a claim about this corpus and this tokenizer, not about relevance. Before trusting any retrieval measurement, run the negative control — the same query set against an empty index and against an index with the target memories removed — so that a filter which can never match and a filter which always matches are both visible. Do not present BM25 ordering as relevance, a passing filter test as retrieval quality, a verified commit as verified content, or a stored symbol as a resolved one. Retrieval quality, semantic similarity, freshness weighting, context-budget packing and any comparison against Supermemory remain later milestones.

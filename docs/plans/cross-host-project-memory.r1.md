# Nexus project memory across Codex, Claude Code, Antigravity and DSH

**Status: proposed for owner approval, 24 November 2026. No implementation or rollout is authorized by this document.**

## 1. Outcome and approval boundary

Approve a folder once. Its Git projects get isolated recall without four separate enrollments. Trust one particular repo for automatic maintenance once, and the preference follows it across compatible hosts. The user can always tell which project is active, what can be saved, and why a write occurred.

Approval of this plan would authorize implementation and testing in isolated checkouts, profiles and stores. It would **not** authorize enrolling a real folder, enabling writes on an owner repo, replacing an installed plugin, changing a live profile, migrating existing memories, or publishing a release. Those need a separate rollout decision. Until plan approval: stop here.

## 2. Proposed owner experience

- **Outside an approved folder:** Nexus stays off. Offer “Enable for this repo” and, separately, “Enable recall for repos under this folder.” No recursive scan, mass enrollment, or background ingestion. Approval controls project memory, not the coding host's own trust prompts or plugin installation.
- **First open under an approved folder:** after the host identifies one trusted checkout, lazily register its opaque project identity. Show `Nexus · <project> · Recall only`. Two hosts opening it simultaneously must resolve the same registration. An empty store can legitimately return nothing.
- **Recall only:** search and read; no memory writes, even through a direct model tool. On an explicit save request, offer a deliberate owner action to authorize the save or enable maintenance; never silently upgrade the repo. In the first implementation use the maintenance toggle rather than building a separate one-shot grant.
- **Preview:** an optional trial inside recall-only. Show “would create,” “would update this record,” or “skip,” with the reason. No durable candidate queue, memory content in telemetry, or delayed write after leaving preview.
- **Recall + maintain:** explicit per-repo opt-in shared across hosts. In v1 an eligible host can automatically create a scoped, owner-stated decision, constraint or procedure. A proposed change to an existing record names the exact record and requires owner confirmation. A host without confirmation UX may show the proposal and leave it unsaved. Explicit saves remain available to authorized root users. No automatic forgetting.
- **Disable:** a per-repo denial overrides folder defaults. Stop new recalls, deliveries and writes, including queued work in already-open sessions. Preserve records; explain that already-displayed text and old session logs cannot be recalled. Re-enabling starts a new policy generation; old queued actions do not resume.
- **Controls:** one owner-facing interface for status, folder approval, repo override, preview and disable; CLI first, native host shortcuts later. Ordinary model tools, repository files and recalled text must not grant permissions. Status shows effective mode, binding, build/capabilities, worker permissions and any degraded behavior, without exposing secrets.

## 3. Shared implementation contract

**Project identity.** Extend the existing [project registry](../../integrations/project_scope/README.md), not four separate path matchers. Resolve from the host-attested workspace or owner pin and verified Git common directory, not the prompt, basename, remote URL or last-opened project. Verify canonical containment and filesystem identity before lazy enrollment. Linked worktrees of an enrolled repo share its project store but verify Git references against the active worktree. An independent clone gets a separate identity even with the same remote. Nested repos and submodules resolve to their own verified identity, never inherit the outer repo’s records. Unknown roots, conflicting signals, escaped paths, unsupported non-Git workspaces and stale identity after a move yield no memory until resolved. A symlink inside an approved folder must not enroll a checkout outside it. Do not silently replace a missing or retired previously enrolled store.

**Enforcement.** All managed reads/writes, host hooks, direct MCP calls and viewers pass through a common project/mode/role check. This includes adapters that now open SQLite directly. A launcher-time check alone is insufficient. Bind work to the project, session role and policy generation; recheck before delivering results and at the write transaction. Define a serialized ordering for opt-out vs. commit: after disable is acknowledged no old-generation write may commit. An already-committed write remains committed. Read-only workers cannot acquire writer authority via a hook. If authorization cannot be verified, the coding turn continues without Nexus. Scope of guarantee: managed integrations, not arbitrary software running as the OS owner.

**Recall.** Once per eligible human prompt, search the current project using bounded lexical input. Skip private/no-memory requests, trivial input and synthetic follow-ups. Show bounded, clearly attributed evidence; IDs-only remains a supported host mode. When delivering body text, check the pinned revision is still current and permitted at delivery. A timeout or changed record means no evidence from that result, not an unbounded retry. Keep explicit history inspection separate. Instrument offers, confirmed reads, skips and latency separately; a hit alone does not establish that a model used a fact.

**Capture and correction.** Consider at most one candidate per completed root turn. Auto-create only from a direct, durable owner statement, not from recalled text, assistant speculation, tool output, transcripts or a routine successful check. Exclude private/no-save turns and likely secrets before any durable write; a heuristic is not a secrecy guarantee. Exact repeats skip. Lexical similarity can nominate an existing decision, never prove identity. An ambiguous match produces a proposal, not a create or overwrite. Confirmation shows old/new text and project; write against the expected revision, preserving intended metadata and references. A conflict invalidates confirmation: reread and present the difference again. Autonomous revisions based on stable decision identifiers are a later proposal, not a v1 dependency.

**Receipts and failure handling.** Attribute writes to project, host, session event, operation, memory ID and revision; keep receipt telemetry content-free. Reading the saved body is an explicit authorized operation. Persist the operation identity before sending a mutation; an identical permitted retry uses the same key and payload. After an ambiguous outcome or project rebinding, pause the operation; reconcile against the verified original store if supported, otherwise report unresolved. Do not generate a new key, repeat from another host, or claim failure/success without evidence. Independent concurrent creates need separate handling: an idempotency key protects one operation, not two hosts independently deciding to save the same fact. Serialize exact-duplicate check/create per project or supply an equivalent tested atomic mechanism. Do not promise semantic deduplication.

## 6. Release-blocking acceptance tests

1. **Four-host handoff:** Claude saves the owner’s staging database decision; Antigravity recalls it; Codex proposes a correction from SQLite to PostgreSQL; the owner confirms the named record; DSH reads its current revision. Expect exactly one record and two revisions. Verify old text only through an explicit history or saved-revision read. If a host cannot confirm natively, exercise its documented deliberate correction route and disclose the limitation.
2. **No false merges:** “staging database” and “staging test database” stay separate. A similar phrase, topic label or shared Git remote must never authorize revising another record.
3. **Isolation:** linked worktree sees the decision; unrelated same-name repo and second clone do not, including by exact ID. Exercise macOS path aliases/case, symlinks, prefix collisions, nested repos, submodules, moved checkout, missing root and retired store.
4. **Opt-out races:** disable from one host while another has recalled-but-not-delivered text and a third has a write waiting. Pending delivery/commit are rejected; open sessions need no restart; re-enable does not replay old work. Existing history survives.
5. **Faults and rights:** duplicate callbacks, concurrent creates, two corrections to one revision, timeout after send, restart, missing end event, missing registry and worker writes. No extra committed revision, no blind retry, no fabricated receipt; missing hooks are shown as unavailable.
6. **Privacy and usefulness:** a recalled instruction cannot select a project or create a fact. Private input, a synthetic credential and test logs produce no automatic record or content-bearing receipt. An empty or slow store cannot block normal coding beyond the agreed budget. Inspect actual injected context and receipt contents, not just tool-call counts.

## 7. Rollout and rollback (not pre-authorized)

Start with a disposable pilot, then one owner-selected repo in recall-only; offer preview before any per-repo write opt-in. Keep the previous artifacts and a verified private backup before any live store-format change. Disable the new hooks/maintenance policy to halt writes; do not roll back by redirecting sessions to the old shared DSH database. Revocation, isolation, wrong-target writes, leaked sensitive content or unresolved store identity are stop conditions. Report the affected build and operation without echoing memory text. No claim of improved coding outcomes from conformance tests alone.

**Decision requested:** approve this v1 scope and the isolated implementation gates, request changes, or hold. Approval does not turn on Nexus in any real repository.

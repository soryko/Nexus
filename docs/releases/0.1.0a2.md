# Nexus Memory v0.1.0a2 — experimental developer prerelease

**The installation no longer needs the source that built it.** v0.1.0a1 installed the
project *editable*: the environment pointed back at the checkout, so moving or deleting the
sources broke the server and the documented verification command along with it. This release
fixes that, and — more to the point — it tests it by deleting the sources and asking again.

Nothing about storage, retrieval or the seven MCP tools changed.

## What changed

**The installer builds a normal installation.** `tools/install.py` now syncs with
`--no-editable --no-dev`: the package is copied into the environment and development
dependencies stay out of a user runtime. The source is needed to build and to upgrade, not
to run.

**The lifecycle checker ships in the package.** `nexus-memory-check` is installed beside
`nexus-memory` and, with no arguments, checks the server next to itself. Verifying an
installation no longer requires a script from a checkout. `tools/check_install.py` remains
as a thin wrapper so the v0.1.0a1 command keeps working, and
`python -m nexus_memory.install_check` runs the same thing. All nine checks, the five-field
receipt comparison, the JSON report and the exit codes are unchanged.

**Each version gets its own environment.** The recommended path is
`--venv "$HOME/.local/share/nexus-memory/venvs/0.1.0a2"`. Upgrading means building a new
environment beside the old one and changing the client's `command` path — which makes
rollback a path change rather than a rebuild. `--venv` still defaults to the checkout's
`.venv` for compatibility; that default is the one case where deleting the checkout still
destroys the environment, and the installer now says which side you landed on.

## What is actually verified

A new CI job on `ubuntu-24.04` and `macos-15` runs
`.github/scripts/check_installed_distribution.py`, which installs from a disposable
`git archive` copy into a separate environment, stores a memory through the installed
package's own MCP client, **deletes that copy**, and only then requires:

- a fresh `nexus-memory-check` process to pass 9/9 against a **new** database — which is
  what exercises the packaged SQL migration resources, not only the Python modules;
- a fresh server on the pre-deletion database to return the same content bytes, the same
  memory and revision identifiers, a search hit, and a whole-receipt replay leaving
  `active_memories` at one;
- the package to import from site-packages, non-editable, in a **new** interpreter, so no
  parent process's import cache can answer for a module that is gone.

Paths contain spaces; `PYTHONPATH` and `PYTHONHOME` are stripped; everything runs outside
every checkout.

**The control that makes this mean something.** The same driver, run in
`--editable-control` mode against the *old* mechanism, passes 9/9 while the checkout exists
and then fails with `ModuleNotFoundError: No module named 'nexus_memory'` once it is
deleted. Same driver, same deletion, opposite outcomes. Without that, a passing result would
only show that the removal step is detectable in principle. Both as-run reports are in
[`docs/measurements/`](../measurements).

**Upgrade from the released alpha.** Checked once, in isolation, on a temporary database: a
memory written and revised by the real `v0.1.0a1` server was read by this candidate with
identical content bytes, the same identifiers, both revisions still in `history`, a working
search hit, and the original receipt replaying without a duplicate — then read again by the
retained old environment, and again from a pre-upgrade backup. That is a compatibility
observation about this installation change. There is no migration tooling and no claim that
a future schema change will be reversible.

## What this release still does not claim

**No benefit to a coding agent has been shown.** That has not changed, and nothing in this
release bears on it. The one held-out comparison that has run found none: across four tasks,
three arms and 36 arm-runs, the memory arm did not beat the no-memory baseline on any task,
lost on one, and cost 1.56× the baseline's combined input and cache-read tokens. A
rendered-notes arm tied on all four.

Durable memory is the product. Improved coding outcomes are not, and are not an acceptance
gate for this release.

**The environment is not relocatable.** A virtual environment holds absolute paths, and this
release does not change that: you may delete the *source*, not move the *environment*. The
Python runtime it was built from must also stay put. Nothing here bundles Python.

Still local, single-user and trusted: no remote authentication, no encryption at rest, no
multi-tenancy. Lexical search covers current revisions only. Linux and macOS; Windows
remains unverified. No PyPI package and no standalone binary in this milestone.

## Install

```bash
git clone https://github.com/soryko/Nexus.git
cd Nexus
git checkout v0.1.0a2
nexus_runtime="$HOME/.local/share/nexus-memory/venvs/0.1.0a2"
python3 tools/install.py --venv "$nexus_runtime"
"$nexus_runtime/bin/nexus-memory-check"
```

Expect `PASS: 9/9 checks`. After that, this clone can be deleted.

Full instructions, the measured per-platform recipes, Claude Code setup, database
locations, backup and the update procedure:
[`docs/experimental-release.md`](https://github.com/soryko/Nexus/blob/v0.1.0a2/docs/experimental-release.md).

## Upgrading from v0.1.0a1

Stop the server → back up → build a new environment → verify → point the client's `command`
at the new executable, keeping your existing `--db`, `--namespace`, `--actor` and any
`--repo` → restart. Keep the old environment until you are satisfied. The full procedure is
in §5 of the release guide.

# Nexus Memory v0.1.0a1 — experimental developer prerelease

**Source prerelease.** Clone a tag, run one installer, connect Claude Code. No PyPI package
and no standalone binary in this milestone.

## What this release claims

An agent stores a fact once and reads it back in a later session, in a different process,
with the same bytes it wrote. That claim is checked mechanically — nine checks across three
separate processes, on every CI run and by the installer you run yourself.

## What it does not claim

**No benefit to a coding agent has been shown.** The one held-out comparison that has run
found none: across four tasks, three arms and 36 arm-runs, the memory arm did not beat the
no-memory baseline on any task, lost on one, and cost 1.56× the baseline's combined input and
cache-read tokens. A rendered-notes arm tied on all four, so the run supports "having the
information helps" no better than "Nexus's retrieval helps."

No retrieval-quality advantage over any other tool has been measured. The v2 evaluation set
scores this build alone, against AI-assessed labels with no human audit at label level.

Durable memory is the product. Improved coding outcomes are not, and are not an acceptance
gate for this release.

## Who it is for

Developers who want durable local memory over MCP and are willing to judge for themselves
whether it helps. It is single-user and locally trusted: no remote authentication, no
encryption at rest, no multi-tenancy.

## Install

```bash
git clone https://github.com/soryko/Nexus.git
cd Nexus
git checkout v0.1.0a1
python3 tools/install.py
.venv/bin/python tools/check_install.py --server "$PWD/.venv/bin/nexus-memory"
```

Expect `PASS: 9/9 checks`. Then connect a client — [`docs/experimental-release.md`](../experimental-release.md)
is the full walkthrough, including the database defaults, the backup procedure and recovery.

**Two independent runtime floors:** Python 3.12+ **and** linked SQLite 3.51.3+. Meeting one
does not imply the other, and a below-floor interpreter fails silently as a closed transport
in your client. The installer probes candidates, reports both numbers, and re-checks the
environment it built.

## Tested configurations

| | |
| --- | --- |
| Platforms | Linux (`ubuntu-24.04`) and macOS (`macos-15` in CI; macOS 26.1 arm64 by hand) |
| Interpreter | uv-managed CPython 3.13.14, linked SQLite 3.53.1 |
| uv | 0.11.21 |
| Client | Claude Code CLI 2.1.270, **user scope**, `Status: ✔ Connected` |
| Tools | `record`, `revise`, `forget`, `get`, `history`, `search`, `status` — none added by this release |

Windows paths exist in code and are **untested**. Other MCP clients take the same stdio
shape but have not been tried.

**Homebrew `python@3.13` did not work on the macOS host tested.** It passes both floors
(3.13.15 / SQLite 3.53.4), but uv refuses it — `platform.mac_ver()` returns empty on macOS
26.1 and uv calls the installation broken. Use a uv-managed interpreter.

## Backup

SQLite's online backup API, documented with a runnable snippet that encodes the source path
with `Path(...).resolve().as_uri()`. That is not cosmetic: a hand-built `file:{path}` URI
containing `#` makes SQLite open a different, empty database and report no error.

Verified against a seeded store in a directory containing spaces and parentheses, backing up
to a filename containing `#`: a new server process started on the copy returned byte-identical
content, the same `memory_id` and `revision_id`, the same `latest_durable_seq`, and found the
content by search.

There is no automatic backup, rotation, restore tooling or migration tooling.

## Known limits

- Search covers **current revisions only**; a term only in a superseded revision will not
  find that memory. Use `history` and `get`.
- Ranking is **BM25 lexical ordering, not relevance**. No embeddings, no semantic similarity.
- A reference filter narrows and never reorders, adds no evidence, never re-verifies on read.
- A verified reference records that an object existed at a commit — **not** that the memory's
  claim about it is true.
- Namespace and actor bind at launch and cannot be overridden by a tool call.
- A source install is **editable**: it points at your checkout. Moving or deleting the
  checkout breaks the installed command.

## Changes in this release

- `tools/install.py` — probes both floors, reports both numbers per candidate, refuses to
  substitute for an explicitly named interpreter, re-checks the environment it built, and
  exits 2 with an actionable message when uv is missing rather than raising.
- `tools/check_install.py` — nine checks over three processes; compares content as UTF-8
  bytes against a sample carrying a newline, a tab, CJK, Cyrillic, a combining sequence and
  an emoji outside the BMP; requires all five receipt fields to replay on an idempotent retry
  while independently confirming no duplicate was written.
- `tests/tools/test_release_tools.py` — failure paths through the real entry points.
- A startup contention repair carried forward from the evaluation branch: a database being
  switched into WAL mode no longer fails a concurrent start.
- CI gains fresh-install jobs on Linux and macOS that run the installer into a previously
  nonexistent environment and then run the lifecycle check from outside the checkout.
